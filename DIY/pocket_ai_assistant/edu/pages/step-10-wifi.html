Step 10: put board A1 on Wi-Fi and get one answer back

The USB prototype passed on 2026-09-20. This step adds the radio and a third-party cloud service. It still produces no spoken output. The goal is one round trip you can see in the log or on the OLED.

Stop unless both are true

Step 9 passed, and you accept that the Xiaozhi/Tenclass bootstrap service receives device metadata and microphone audio. The setup hotspot is open, the form is plain HTTP, and the credentials you type are stored unencrypted in flash until a full reflash. Do this in a private place, on a dedicated 2.4 GHz guest network with a unique password.

Radio note for this board

The SuperMini's ceramic chip antenna is poorly matched. At the firmware's default 20 dBm the setup hotspot was invisible on three boards from this batch, including A1, even with the phone touching the board. The assistant build therefore caps transmit power at 8.5 dBm, once for the hotspot and once for the normal connection, and logs it each time. That is lower power, not higher. Expect short range and keep the phone close.

The three gates

Each gate is a checkpoint you record. Nothing on this page marks a gate passed for you.

Pass 10A

Safe to flash. Build, verifier and preview all say assistant mode, amplifier disabled, right port.

Pass 10B

On your network at capped power. Hotspot seen, form accepted, station cap line, then Connected to WiFi.

Pass 10C

One round trip. A quick press listens, one question, one remote answer, no reset.

What the radio does, and where the cap applies

The firmware starts the radio twice: once as a hotspot so your phone can hand it the network, and again as a normal station to join that network. The transmit-power cap only takes effect after a start, so it is applied after each one. Knowing this tells you which log line to expect at which moment.

Before you start

  • Step 9 passed, and the Step 9 wiring is untouched. Add nothing.
  • A dedicated 2.4 GHz guest/IoT network exists with a unique password, and the router confirms it broadcasts on 2.4 GHz. The ESP32-C3 cannot see 5 GHz.
  • You are in a private place. Nearby people could observe the open hotspot and the plain-HTTP form.
  • The phone is in hand, and you can turn its mobile data off for the setup minute so the captive portal is not bypassed.
  • You know the exact serial port from Step 3. The commands below say /dev/ttyACM0; replace it with yours.

Part 1: build, verify, preview

  1. Read the assistant-mode privacy and provisioning notes in the firmware README (firmware/README.md, section "Flash and monitor source builds").

  2. Prepare the dedicated 2.4 GHz guest/IoT network and confirm on the router that it is 2.4 GHz.

  3. Leave the Step 9 wiring exactly as it passed.

  4. With the existing USB-only hardware, build assistant mode. If this prints an error, stop; never run a later command against an older artifact.

    . firmware/.work/esp-idf/export.sh
firmware/scripts/build.sh --assistant

  5. Verify the build. Stop unless it prints Build mode: assistant; amplifier: disabled with no error.

    python3 firmware/scripts/verify_source_build.py

  6. Preview the flash on the exact port from Step 3.

    firmware/scripts/flash.sh /dev/ttyACM0 --dry-run

Part 2: flash, find the hotspot, hand over the network

  1. Flash and open the monitor.

    . firmware/.work/esp-idf/export.sh
firmware/scripts/flash.sh /dev/ttyACM0 --monitor

  2. In the boot log, find these three lines in this order. Other lines appear between them and the numbers in parentheses vary. Write down the exact hotspot name; its last four characters differ per board.

    I (…) WifiManager: Starting config AP
I (…) WifiConfigurationAp: Access Point started with SSID Xiaozhi-XXXX
I (…) WifiBoard: Wi-Fi max TX power capped at 8.5 dBm (provisioning AP)

    If the third line is missing, the board is running an older image at full power, the exact condition that was invisible on this batch. Go back to item 4 and rebuild.

  3. The OLED shows the Wi-Fi configuration screen with the same hotspot name and the address http://192.168.4.1.

  4. On the phone, turn mobile data off. Hold the phone within 30 cm of the antenna end, open the Wi-Fi list, and wait up to 30 seconds. Pull down to rescan if the list does not refresh. The hotspot is open, with no password. Join it. If the phone warns that the network has no internet, choose to stay connected.

  5. If the captive portal does not open by itself within 15 seconds, open a browser and go to http://192.168.4.1.

  6. In the form, choose your 2.4 GHz guest network from the scanned list, type its password, and submit. The board switches to that network's channel to test the credentials. If the router refuses the first attempt, the firmware waits three seconds and tries once more by itself, so wait for the page's result before touching anything. The phone drops off the hotspot when the board reports success. That is expected.

  7. Back in the monitor, find these lines in this order.

    I (…) WifiBoard: Starting WiFi connection attempt
I (…) WifiBoard: Wi-Fi max TX power capped at 8.5 dBm (station)
I (…) WifiBoard: Connected to WiFi: <your guest network>

    If the board instead logs WiFi connection timeout, entering config mode, it could not reach the router at 8.5 dBm. Move the board and the router into the same room and repeat from item 10.

Part 3: activation and one round trip

  1. Keep watching the monitor and the OLED. Once on the network the firmware contacts the third-party bootstrap service. Ota: Activation successful in the log means the service already knows this board. Otherwise the display or log shows an activation instruction, usually a short code to enter on the service's own site. That flow belongs to the third party and may change independently of this repository. Enter the code only on the service's own activation page.

  2. Give the external GPIO10 button one quick press. When the log or display shows that it is listening, ask one short question such as "What is two plus two?" Wait for a remote response to appear in the log or display. Quick-press the button once more if the interface remains active.

If the hotspot never appears

Work down this tree and stop at the first branch that changes the result.

Return to offline diagnostics

Do this whenever you need to isolate a hardware problem, and before a provisioned board leaves your control. The diagnostics reflash writes this project's blank NVS area, which clears the saved Wi-Fi credentials. A reset does not.

. firmware/.work/esp-idf/export.sh
firmware/scripts/build.sh --diagnostics
python3 firmware/scripts/verify_source_build.py      # expect: Build mode: diagnostics; amplifier: disabled
firmware/scripts/flash.sh /dev/ttyACM0 --dry-run     # expect diagnostics, amplifier disabled, right port
firmware/scripts/flash.sh /dev/ttyACM0 --monitor

Stop at any command that prints an error. Never run a later command against an older artifact.
