# Drone firmware audit and verification

The original video firmware has a reproduced radio-loss defect that commands maximum throttle. The recommended Wi-Fi design uses the creator's newer ESP-FLY hardware and ESP-Drone fork instead. This package contains a small, reviewable ESP-FLY patch and host regression tests. Physical response, radio range, controller tuning, motor waveforms, and battery behavior still require the assembly acceptance tests; source inspection and compilation cannot establish those results.

## Source identity

ESP-FLY source is [Seeed-Projects Co-Create ESP-FLY](https://github.com/Seeed-Projects/Co-Create_ESP-FLY/tree/96de4d78c4d9e561c6a7ade2865a13f16b519ac3), pinned to commit `96de4d78c4d9e561c6a7ade2865a13f16b519ac3`. Paths below are relative to `Firmware/esp-drone`. The repository includes historical Windows build products; those are upstream artifacts, not evidence that this workspace built or tested anything. Their IDF metadata identifies the 5.0.7 family. The patch is separate from the vendor's prebuilt binary.

The original Arduino files came from the [creator's public Drive folder](https://drive.google.com/drive/folders/1RpVh6NTzbtIL2lJVP0EqVGJy4QKX_Syh). The inspected `NRF24_RX.cpp` SHA-256 is `e60ce122795fd2d709c9a46cf87366ad296d76254d53ff0ac65c9b0a92f3280f`. References to original filenames and line numbers identify that snapshot. Its sketch header credits an ELECTRONOOBS modification dated 11 April 2020, based on earlier MultiWii/iforced2D work; the header is not a certification of the video build.

## ESP-FLY findings and changes

| Finding | Evidence in pinned stock source | Consequence and package action |
|---|---|---|
| Stock command watchdog levels after more than 500 ms and stops after more than 2000 ms | `components/core/crazyflie/modules/interface/commander.h:35`; `modules/src/commander.c:104–129` | During the leveling interval, thrust remains unchanged. The supplied patch makes these configurable, defaulting to 300 ms and 500 ms. These are proposed indoor test settings, not measured limits or a guaranteed landing routine. |
| Startup and reconnect require a zero-thrust command | `modules/src/crtp_commander_rpyt.c:162–180` | A nonzero command is suppressed while locked. The commander resets priority on timeout, causing the legacy decoder to relock. Host tests check normal start, timeout, reconnect and zero-thrust recovery. This is a thrust lock rather than an independently authenticated arm switch. |
| Startup self-test powers motors before normal control | `components/drivers/general/motors/motors.c:157–178`; `motors/include/motors.h:74` | Stock test requests about 20% ratio sequentially. The patch disables automatic motor pulses by default and preserves the explicit configuration option. A stock binary can still pulse motors when powered. |
| UDP receive accepts invalid lengths | `components/drivers/general/wifi/wifi_esp32.c:144–160` | Zero length reaches an index of minus one; longer valid-checksum packets can exceed the CRTP structure. The patch requires 2–32 bytes total: header, at most 30 data bytes, checksum. |
| Wi-Fi to CRTP copy lacks its own bounds check | `components/core/crazyflie/hal/src/wifilink.c:115–118`; `modules/interface/crtp.h:33–75` | Raw CRTP capacity is 31 bytes. The patch checks 1–31 bytes again before copying. This independently protects the queue-to-parser boundary. |
| Legacy control decode does not validate payload size | `modules/src/crtp_commander.c:110–117`; `crtp_commander_rpyt.c:47–53` | A valid packet contains three floats and one 16-bit thrust value, totaling 14 bytes. The patch rejects other sizes before decoding or updating command freshness. |
| Legacy control floats can propagate invalid values into the controller | `crtp_commander_rpyt.c:223–240`; `modules/src/controller_pid.c:88–92` | The patch rejects NaN and infinities, and rejects roll/pitch beyond ±45° and yaw rate beyond ±360°/s before refreshing freshness. Those bounds are deliberate Angle-profile limits; tests cover each axis, invalid numeric values, both bounds and watchdog expiry after malformed traffic. |
| Public Wi-Fi credentials and three simultaneous clients | `wifi_esp32.c:28–31,229–258` | The patch requires a private 12–63 character password, selects WPA2, allows one associated client, and removes the password from log output. This is access control, not application-layer packet authentication. |
| Battery shutdown is unimplemented | `components/core/crazyflie/hal/src/pm_esplane.c:157–162,402–417` | `pmSystemShutdown()` contains a TODO, not a working cutoff. Default low/critical thresholds of 3.2/3.0 V and their five-second timers do not establish battery protection. Calibrate voltage indication and land manually before excessive sag. |
| ADC configuration label is stale | `sdkconfig:481`; `components/drivers/general/adc/adc_esp32.c:39–40,60–75`; `pm_esplane.c:120` | Runtime S3 ADC input is GPIO2 regardless of the nominal `CONFIG_ADC1_PIN=10` setting. The actual battery multiplier is 2. The creator's 10 kΩ/10 kΩ divider to GPIO2 agrees with this runtime code. The build profile changes the label to 2 to avoid misleading wiring instructions. |
| Default UART console shares a pin with the red LED | `sdkconfig:490,958–975` | S3 UART0 TX defaults to GPIO43, also configured as the kit's red LED. The build profile selects native USB Serial/JTAG for the application console. ROM boot output may still briefly toggle the pin. |
| Stock configuration permits mode changes for optional sensors | `sdkconfig:444–445`; `crtp_commander_rpyt.c:91–122` | The kit has an IMU but no flow/range/GPS package. The build profile disables position-hold selection and command mode switching; use manual throttle and Angle mode. |

Direct source entry points: [commander](https://github.com/Seeed-Projects/Co-Create_ESP-FLY/blob/96de4d78c4d9e561c6a7ade2865a13f16b519ac3/Firmware/esp-drone/components/core/crazyflie/modules/src/commander.c#L104), [legacy control decode](https://github.com/Seeed-Projects/Co-Create_ESP-FLY/blob/96de4d78c4d9e561c6a7ade2865a13f16b519ac3/Firmware/esp-drone/components/core/crazyflie/modules/src/crtp_commander_rpyt.c#L162), [Wi-Fi transport](https://github.com/Seeed-Projects/Co-Create_ESP-FLY/blob/96de4d78c4d9e561c6a7ade2865a13f16b519ac3/Firmware/esp-drone/components/drivers/general/wifi/wifi_esp32.c#L134), [battery implementation](https://github.com/Seeed-Projects/Co-Create_ESP-FLY/blob/96de4d78c4d9e561c6a7ade2865a13f16b519ac3/Firmware/esp-drone/components/core/crazyflie/hal/src/pm_esplane.c#L157).

The default radio endpoint remains `192.168.43.42:2390/UDP`, AP name `ESP-DRONE_` followed by MAC bytes, 2.4 GHz channel 1. The code adds an eight-bit additive checksum, which detects some corruption but provides neither packet authentication nor replay prevention. One-client WPA2 reduces exposure; it does not turn the old CRTP stack into a comprehensively audited network service. Other CRTP ports, generic command decoders and malicious-client behavior are outside this small patch. The engineering release remains for controlled prototype testing.

## ESP-FLY motor control and tuning

The source drives four LEDC channels at 15 kHz, using eight-bit PWM (`motors.c:108–113`; `motors/include/motors.h:39`). This is direct brushed-motor duty control through MOSFETs, not a brushless ESC pulse protocol. The 16-bit control demand is shifted to eight bits; a displayed 16-bit command does not provide 16-bit physical PWM resolution. `ENABLE_THRUST_BAT_COMPENSATED` is commented out, so battery compensation is not active despite the function being present.

The pinned `sdkconfig` maps M1/M2/M3/M4 to GPIO7/4/3/1. The creator's wiring drawing places them front right/rear right/rear left/front left, respectively. Verify actual motor location and corrective response before attaching props; this order differs from the original Arduino quad. The selected platform setting retains the historical name `TARGET_ESP32_S2_DRONE_V1_2` even though the MCU target is ESP32-S3. Selecting a fresh board default can silently change the motor and sensor pins.

The selected PID constants are inherited from `modules/interface/pid.h:33–62`: roll and pitch rate P/I/D are 190/440/2.6; yaw rate 120/16.7/0; roll and pitch angle 5.3/2.5/0; yaw angle 6/1/0.35. These numbers use this controller's units and integration conventions, so they must not be copied into MultiWii, Betaflight or a new PID implementation. The patch does not retune them. Different motor/prop combinations, a flexible printed frame, a shifted battery or a camera can change stability and demand retesting.

## Original video firmware findings

| Finding | Source line evidence | Engineering assessment |
|---|---|---|
| Radio loss requests maximum throttle | `NRF24_RX.cpp:25,79–84` | Reset sets byte throttle to 0; the reversed map turns 0 into 2000. After more than 1000 ms without reception, an already armed aircraft can receive full throttle. Four host assertions execute the actual reset and receiver functions and reproduce this defect. |
| Standard failsafe is disabled | `config.h:601`; `NRF24_RX.cpp:61–92`; `MultiWii.cpp:878–893` | Simply uncommenting `FAILSAFE` is insufficient: this radio adapter never maintains the standard fresh-reception counter. A reviewed integration must connect valid packets to the state machine and prevent automatic rearm. |
| Roll and yaw names are crossed | `NRF24_RX.cpp:85,87`; transmitter `:115–118` | Byte `yaw` controls ROLL and byte `roll` controls YAW. Physical joystick wiring may compensate, but a replacement transmitter cannot rely on the struct labels. |
| Receiver and transmitter structs differ | `NRF24_RX.h:20–28`; transmitter `:30–37` | Seven bytes versus six; the receiver includes unused `switches`. Static padded payload behavior may conceal the difference, so it is not proof of a radio failure. Use one explicitly versioned wire format and fixed payload length. |
| Telemetry comments and implementation disagree | `NRF24_RX.cpp:54–55,65–76` | Auto-ACK is disabled, ACK payload enable is commented out, and coordinates are fixed constants. This is not verified return telemetry or GPS. |
| Low-battery measurement is disabled | `config.h:896–902` | Retained thresholds are for 3S batteries, not a 1S microdrone. Transmitter LCD voltage is its own A7 divider reading, not drone voltage telemetry. |
| Motor ordering is specific | `Output.cpp:21,1194–1198` | Motor0 = rear right D9; motor1 = front right D6; motor2 = rear left D5; motor3 = front left D3. Do not substitute ESP-FLY numbering. |
| PWM uses hardware and software paths | `Output.cpp:425–453,687–702,1040–1105` | D9/D3 use hardware timers; D5/D6 use timer0 compare interrupts. Changing only the `PWM_PIN` array does not remap the waveform implementation. |
| Firmware clock is not a trivial substitution | `NRF24_RX.h:1`; `config.h:83`; `Output.cpp` timer code | Header says tested with 16 MHz ATmega328P. A properly built 8 MHz variant changes PWM carrier and available loop time. Selecting the wrong `F_CPU` also invalidates timing. Neither frequency variant was target-compiled or bench-tested here. |
| Orientation and mode settings need commissioning | `config.h:171,205,226,232,237`; `EEPROM.cpp:179`; `MultiWii.cpp:1060–1068` | MPU6050, forced gyro axes, PID controller 1, flat-only arming and yaw-stick arming are configured. Fresh mode activation masks are zero, so Angle mode is not enabled merely because an accelerometer exists. EEPROM/calibration state matters. |

For the active default PWM path, arithmetic reduces a 1000–2000 motor command to compare values 0–250. Under the usual 16 MHz AVR core timer setup, the nominal carrier is about `16 MHz / (64 × 510) = 490.2 Hz`, and maximum duty is approximately `250/255 = 98.0%`. At 8 MHz the nominal carrier halves. These are source-derived calculations, not oscilloscope measurements; interrupt latency, update races and actual core timer initialization still matter. Optional higher-frequency macros cannot be enabled blindly because the unconditional brushed remapping precedes their separate transforms.

The original source does set disarmed commands to `MINCOMMAND=1000`, which the brushed remap turns into zero demand (`Output.cpp:1615–1616,425–428`). That behavior does not neutralize the armed radio-loss defect. The correct response is to withhold the original firmware from flight, not to infer that successful startup or a short demonstration validates every loss-of-control condition.

## Verification performed and limits

`tests/firmware_audit.py` extracts the real commander, legacy decoder and callback bodies from the selected source and compiles them with `g++` against deterministic queue/time stubs. The patched default profile passed 84 control assertions and 128 UDP-length assertions. The original receiver passed four assertions reproducing its unsafe timeout mapping using the durable fixtures in `sources/legacy-audit`; passing a defect-reproduction test means the defect exists, not that that firmware is acceptable.

Tests cover zero-thrust startup lock, thrust cap and dead zone, yaw sign, exact timeout boundaries, retained thrust during leveling, zero thrust after the stop deadline, reconnect lock, unsigned tick wraparound, rejection of all non-14-byte legacy payload lengths from 0 to 30, rejection of NaN/infinite/out-of-range inputs on each axis, acceptance of exact numeric bounds, and expiry despite malformed traffic. The UDP test executes the actual patched length expression for lengths 0 through 127. Static checks verify the second CRTP bounds guard and the private WPA2/one-client settings. The queue stubs do not model FreeRTOS scheduling, electrical faults, IMU faults or real radio latency.

Target build results and reproducible setup are recorded in [the firmware instructions](../firmware/README.md). A successful target build proves toolchain compatibility and linking, not successful flashing, loop timing under Wi-Fi load, brownout recovery, or flight stability. The design acceptance plan must still demonstrate motors remain off through power-up/reset, physical command loss reaches zero PWM within the configured deadline plus measured scheduler delay, reconnection cannot restart them without zero throttle, and measured voltage agrees with a meter.
